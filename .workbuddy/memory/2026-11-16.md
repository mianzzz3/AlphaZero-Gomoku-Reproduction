## AlphaZero-Gomoku 复现代码审查

审查全部源码 + `gpu_run_20261113_104802/` 日志、指标、模型文件，产出 `CODE_REVIEW.md`（仓库根目录）。

**核心结论：训练实际失败，价值网络失效。**

从日志量化出的事实（此前未被发现）：
- `explained_var` 只在**前 24 个自对弈 batch** 有非零值（峰值 0.778 在第 2 个 batch），此后 2370 局恒为 `0.000`；`value_loss` 锁死在 `1.000`。价值头输出恒为常数 0（`RESULTS.md` 记为"价值预测均约 0.0225"，实际是失效证据）。
- `episode_len` 从 36 降到 18，最小值 9（9 手 = 先手 5 手连五、后手不防守）→ 自对弈退化成"先手背诵胜利脚本"。
- `entropy` 3.85 → 2.31（10×10 均匀熵 4.605）。

**代码层面确认的缺陷（均带行号写在 CODE_REVIEW.md）**：
1. `game.py:194` 自对弈永不换边（`init_board()` 无参数）→ 通道 3 与"我是 player1"共线，价值函数无法区分先手后手。这是退化根因，改一行即可。
2. `game.py:66-72` 用 `% self.height` 应为 `% self.width`，4 处。实测 4×6 棋盘 move=9 被写到 (1,3) 而非 (3,1)。方棋盘下不暴露。
3. `game.py:73` 颜色通道按 `len(states)%2` 判断，`start_player=1` 时语义反转；`policy_evaluate` 会轮换先手 → 评估时 OOD。
4. `train.py:124` `lr_multiplier < 10` 判断在乘法前，实际上限是 15。CPU 那轮卡在 11.391 → 实际 lr = 0.0228（初始值的 11 倍），这是 CPU 版 loss 一直 5.2–6.5 的直接原因。
5. `human_play.py` 只能加载 Theano pickle 模型（`80 02` 头），无法加载自己训练的 torch 模型（`50 4b` 头）；numpy 版 conv 按 Theano 翻转权重写，即使读出来也算错。
6. `policy_value_net_pytorch.py:77` `torch.load` 无 `map_location`；`train.py:55,60` 硬编码 `use_gpu=True` 无可用性检查。
7. `RESULTS.md` 说根目录 `best_policy.model` 与 `current_policy.model` 权重相同 —— **错**。逐成员 md5 比对：根目录 16 个张量全不同；`gpu_run_*/` 里那一对才是 16/16 相同。

**性能瓶颈排序**：每次 playout 的 `copy.deepcopy` > 无 `no_grad` 的单样本前向 > 每 epoch 全 batch 前向算 KL > `has_a_winner` 每步重建 set（纯 MCTS rollout 的主要开销，评估成本可能超过全部自对弈）。

验证手段备忘：用 `encoding='bytes'` 才能 pickle.load 上游模型；`best_policy_8_8_5.model` 空盘 value=0.287、policy 熵 2.26（均匀 4.16），确认上游模型可用。

### 根因锁定（补做 10×10 判别实验后）

10×10、固定先手、400 playout、lr 固定 2e-3，只跑 60 局：corr(v,z) 第 10 局 **0.89**，第 60 局 0.81，v_std 0.75，vloss 0.39。原版同棋盘同先手同 playout 是 2399 局 corr ≡ 0、vloss ≡ 1.00。

6×6 上再补一组「固定先手 + 全程 temp=1」消融：corr 0.74。**换边、温度衰减都不是必要条件**，三组都活。

→ **根因是学习率被 KL 自适应锁死**：`kl_targ=0.02` 使「降」阈值 0.04、「升」阈值 0.01，实测 KL 稳定在 0.025，两条分支都不触发 → `lr_multiplier` 冻结在 0.088，有效 lr = 1.76e-4。CPU 那轮是镜像故障（KL 0.0004 → 一路 ×1.5 → 11.39 → lr 0.0228）。同一段代码两个方向都跑偏。

### 图形化人机对战（web_play.py）

用户要「图形化」。选了 Web 方案（本地 http.server + 内嵌 HTML/Canvas），不是 tkinter —— 这台机器没有可靠显示环境，Web 还能用内置浏览器预览。MCTS 留在 Python 进程，前端只渲染；对局状态由服务端单例 `Session` 持有，刷新不丢局。

API：`/api/new|state|move|ai|undo|hint|models`，`ThreadingHTTPServer` + 全局锁。首屏状态由 `render_page()` 内联成 `window.__BOOT__`，避免等两个 fetch 才出棋盘。

三个坑（都踩过）：
1. **候选概率不能用 `get_move_probs` 的返回值**。`temp=1e-3` 时 `softmax(1000*log(visits))` 是 one-hot，展示出来是 100%/0%/0%。改用访问数占比（= temp=1 的 π）。
2. **`fit()` 不能量 `.boardwrap.clientWidth`**：canvas 就在 wrap 里，会形成「越画越小」的反馈回路。改量 `.left`。
3. **热区不能画大圆盘**，多透明都会被误读成棋子。改成小圆点（半径按 share）+ 首选加虚线环，且只画前 8 个（10×10 模型会摊到 84 个点）。

验证手段：直接用 `~/.cache/puppeteer/chrome/*.zip`（已损坏，解压失败）不行，改用系统 `firefox --headless --screenshot`，配合 `MOZ_HEADLESS=1` + 独立 profile。截图确认了棋盘/棋子/五连红线/终局状态/响应式布局。

界面顺带暴露了一个比曲线更直观的结论：8×8 上游模型 400 模拟只访问 **2~4 个点**；10×10 那份（价值头失效）访问 **84/96 个点**，前三合计仅 6%，`v` 恒定 +0.057 —— MCTS 实际在「均匀采样」而不是「挑点深算」。

### 局域网访问（--host 0.0.0.0 + 令牌）

用户要「在其他环境打开」。这台是本地 Arch（wlan0 10.4.178.31/18 校园网），不是 WSL/远程，所以就是手机/平板同 WiFi 访问。

改动：
- `--host 0.0.0.0` 时自动生成 `secrets.token_urlsafe(6)`，打印带 `?t=` 的链接；**回环地址免令牌**，局域网必须带，否则 401。
- 首次带 `?t=` 访问 `/` 时种 `gp_tok` cookie，后续 fetch 靠 cookie（`credentials:'same-origin'` 显式写上）。
- `--no-token` 可关。

两个隐蔽 bug（都踩了）：
1. **不能用 UDP `connect` 探出口 IP** —— 这台机器装了 FlClash，探出来是 `198.18.0.1` 假地址。改读 `ip -4 -o addr show scope global`，按网卡名排序（`wl*` 优先），排掉 `docker/br-/virbr/veth/tun/tap/wg/zt/FlClash` 和 `198.18.*`。
2. **`free_port` 的探测 socket 必须设 `SO_REUSEADDR`** —— 上次运行残留的 keep-alive 连接停在 CLOSE-WAIT/FIN-WAIT-2，不设就绑不上 8777，服务被无声挤到 8778（`HTTPServer` 自己设了 `allow_reuse_address`，本可以绑）。这个坑让预览面板指着 8777 却打不开，排查了两轮。

已验证：本机 200 / 局域网裸访问 401 / 带令牌 200+Set-Cookie / cookie 下 POST 落子正常；firefox 走局域网地址截图确认渲染正常。

语义提醒：服务端单例 Session，所有设备看到同一局，手机上重开会清掉电脑那盘。已在文档写明。
